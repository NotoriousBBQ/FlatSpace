# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FlatSpace is a simple turn-based 4X strategy game built in **Unity 6000.4.1f1** (Unity 6.4) using the
**Universal Render Pipeline (2D)** and **UI Toolkit** for the in-game HUD. The core loop is an AI-driven
economic simulation: planets produce and consume Food, Grotsits, Industry, and Research each turn, and
per-player AI reacts by issuing shipment / colonization / production / research orders.

Gameplay is not designed around a human player taking actions — every player is currently AI-driven. The
game runs the simulation forward on a timer or one turn at a time.

## Building, running, and checking code

There is no command-line build. Work through the Unity Editor or Rider:

- **Compile / check for errors:** use the Rider MCP tools — `mcp__rider__build_solution_start` +
  `mcp__rider__build_solution_state`, or `mcp__rider__get_project_problems` for the current
  compile/inspection problem list. `FlatSpace.sln` is the solution; game code lives in
  `Assembly-CSharp` (`.csproj` files are git-ignored and regenerated by Unity/Rider).
- **Run the game:** open the project in Unity and enter Play mode from `Assets/Scenes/MainMenu.unity`.
- **ReSharper/Rider settings** are committed in `FlatSpace.sln.DotSettings` (note: the `.user` variant is
  git-ignored).

### Tests

There are **no automated tests**. `com.unity.test-framework` is a dependency but no test assemblies or
test files exist. Files/assets with `Test` in the name (e.g. `CameraSaveTest.json`,
`PrimePlanetTypeDataPopTest.asset`, `MapDesignerTest.unity`) are ad-hoc fixtures, not a test suite.

## Scenes and flow

`Assets/Scenes/`: `MainMenu` → either `Flatspace` (the game) or `MapDesigner` (the board editor).

**Scene name strings are load-bearing.** `SaveLoadSystem` and `Gameboard` look scenes up by literal name
(`"Flatspace"`, `"MapDesigner"`) via `SceneManager.GetSceneByName` / `LoadScene`. Renaming a scene file
requires updating those strings and the build settings scene list.

## Architecture

### Simulation vs. presentation

The simulation is deliberately separated from the visuals:

- **Simulation:** `GameAI` → `GameAIMap` → `Planet`, plus `Player` → `PlayerAI` and the `Catalog` system.
  These are `MonoBehaviour`s but they are **created at runtime with `this.AddComponent<T>()` and stacked
  on a small number of GameObjects** (mostly the `Gameboard` object and the `GameAI` object). There is no
  GameObject-per-planet in the simulation — a `Planet` is just a component in a `Dictionary<string, Planet>`
  keyed by planet name. Planet names are the universal identifier throughout orders, pathing, and saves.
  A planet's docked ships are represented by `Ship` (`Assets/Flatspace/Objects/Ships/Ship.cs`) — one class
  covering both kinds via a `ShipKind` enum (`ColonyShip`/`WarShip`), with `Owner`, a `Template` (`ShipData`),
  and a `ResearchSnapshot` (the owner's completed Ship Improvement research at construction time). Ships live
  in `Planet.DockedShips`, created with `Planet.DockNewShip`/`.DockShipFromSave` and removed with
  `.UndockShip`; this replaces the old `Planet.HasColonyShip` bool.
- **Presentation:** `PlanetUIObject` (world-space planet markers), `LineDrawObject` (connection / order
  lines), and the UI Toolkit HUD (`MainScreenUIController`, `NotificationListController`,
  `PlanetDetailUIController`, `GameButtonHandler`). `Gameboard.Update()` closes the planet detail
  panel on any click that lands neither on the panel itself (`PlanetDetailUIController.ContainsScreenPoint`)
  nor on a planet (an `EventSystem.RaycastAll` check, mirroring the raycast that drives
  `PlanetUIObject.OnPointerClick`) — the same effect as pressing Escape.

`Gameboard` (class name is `Gameboard`, **not** `GameBoard`; namespace `FlatSpace.Game`; file
`GameBoard.cs`) is the central singleton (`Gameboard.Instance`) that owns both sides and drives the turn.

### The turn loop

`Gameboard.SingleUpdate()` (called once, or repeatedly by the `TimedUpdate` coroutine) does:

1. `GameAI.GameAIUpdate()`:
   - `ProcessCurrentOrders()` — decrement `TimingDelay` on in-flight orders, execute and remove any that hit 0.
   - `UpdateAllPlanets()` — each `Planet.UpdatePlanet()` runs its economy and appends
     `Planet.PlanetUpdateResult` entries (shortages, surpluses, colonizer-ready, production-complete, …).
   - `ProcessResults()` — hands the result list to each `Player` → `PlayerAI`, which appends new
     `GameAI.GameAIOrder`s.
   - `ProcessNewOrders()` — queue delayed orders, execute immediate ones.
2. Bump `TurnNumber`, then refresh the presentation layer (`PlanetaryUIUpdate`, `BoardUIUpdate`,
   notifications, order lines).

### Orders

`GameAI.GameAIOrder` is the unit of change: an `OrderType`, an `OrderTimingType` (Immediate / Delayed /
Hold), `TimingDelay` / `TotalDelay` (in turns; delay is roughly `path.Cost / defaultTravelSpeed`),
`Origin` / `Target` planet names, `PlayerId`, and a **`Data` field typed `object`** (boxed `int` or
`float` — code branches on the runtime type, and saves record `dataType` as `"int"`/`"float"`). Every
resource move is expressed as a trio of orders: a delayed transport, an immediate deduction at the
origin, and an immediate "in progress" flag.

`OrderType` also has `OrderTypeShipTransport`, added for the concrete `Ship` representation — it's
mechanism-only so far (`GameAI` knows how to execute it, but nothing in `PlayerAI` creates one yet; a
future task is expected to add that AI logic). Because `OrderType` serializes as a `JsonUtility` int,
new values must always be appended last, never inserted.

### Decision-making: `ScoreMatrix`

`PlayerAI` makes every choice through the generic
`ScoreMatrix<TDecisionElement, TChoiceElement, TAction>` (`Assets/Flatspace/GameAI/ScoreMatrix.cs`).
A matrix maps decision rows (e.g. "this planet needs food") to a list of scored choice elements (e.g.
"ship from planet X at cost C"). `GenerateActionList()` sorts each row's choices, then greedily assigns
the best choice per row while removing that choice from all other rows so the same surplus isn't spent
twice. `ScoreMatrixMultipleDecisionElement` allows a row to claim more than one choice (`NumChoices`).
The lightweight wrapper types `ResourceMatrix.cs` / `IndustryMatrix.cs` / `ResearchMatrix.cs` just define
the element/action structs for each use.

### Pathing

`PathingSystem` (singleton that lazily creates its own GameObject) builds a node graph from planet
positions — an edge exists between two planets within `MaxConnectionSize` (400) — and runs A*.
`GameAIMap` precomputes **all-pairs** paths at init and stores per-planet lookup tables in
`Planet.DistanceMapToPathingList` (cost + node count). `PlayerAI` gates shipments/colonization on
`NumNodes <= GameAIConstants.maxPathNodesForResourceDistribution`.

Connections are now first-class data: `PathingSystem.InitializePathMap` builds the graph from each
`Planet.Connections` list (explicit edges) when any planet carries one, and falls back to the historical
"edge between every pair within `MaxConnectionSize` (400)" rule only when no planet has explicit
connections. Explicit connection lists originate from the board designer
(`PlanetDesigner.connectionNames` → `BoardDesignerSave` → `PlanetSpawnData._connections` →
`Planet.Connections`), including from the procedural generator (`MapGenerator` /
`BoardDesigner.GenerateRandomBoard`).

### Data: ScriptableObjects and JSON catalogs

- **ScriptableObjects** hold tuning/spawn data: `BoardConfiguration`, `PlanetSpawnData`,
  `PlanetResourceData` / `PlanetTypeData`, `GameAIConstants` (travel speed, morale step, expansion
  trigger, per-strategy `ModifierListForPlanetStrategy`, per-type resource data), and `CatalogItem`.
  `Assets/GameAIConstants4ProductionTypes.asset` is the active constants asset.
- **Catalogs** (`Catalog.cs`): the Research and Production tech/build trees, loaded from JSON at runtime
  (not from ScriptableObjects). Editor path: `Assets/Flatspace/Catalogs/{Research,Production}/`; runtime
  path: `Application.persistentDataPath/Catalogs/`. `CatalogItem.researched` is a single flag meaning
  "unlocked/completed" for both trees; completing a research item also flips `researched` on production
  items whose `requiredTech` matches. Edit catalogs via the **Save/Load Catalog buttons** added to the
  `Catalog` component inspector by `Assets/Editor/CatalogEditor.cs`.

### Saves

`SaveLoadSystem` (singleton) serializes with `JsonUtility` and uses the **SimpleFileBrowser** plugin
(`Assets/Plugins/SimpleFileBrowser/`) for in-game file dialogs. Two save shapes: `GameSave` (full
simulation state — planets, orders, per-player catalogs & research progress, camera) and
`BoardDesignerSave` (planet name/type/position list from the designer). Paths differ by build:
`Application.dataPath/Flatspace/...` in the editor, `Application.persistentDataPath/...` in a player.
`BoardConfiguration` assets are loaded through **Addressables**. `GameSave.PlanetSave` also carries a
`dockedShips` list (kind, owner, and research snapshot at construction time) for each planet's `Ship`s.

### Board designer

`MapDesigner` scene + `BoardDesigner` / `PlanetDesigner`. Place planet GameObjects as children, then use
the component context-menu actions "Generate Connections" and "Generate Names And Strategies" (which
assigns a default `PlanetStrategy` per `PlanetType`), and save to a JSON board config that the game loads
to start a new match.

### Input

New Input System. `Assets/Game/Input/MapInputActions.cs` is the generated C# wrapper for the map action
map; `Assets/InputSystem_Actions.inputactions` is the project-wide action asset. Regenerate the wrapper
from the `.inputactions` asset rather than editing it by hand.

## Conventions and gotchas

- **Namespace casing is inconsistent** and both spellings are in use: `FlatSpace` (e.g. `FlatSpace.AI`,
  `FlatSpace.Game`, `FlatSpace.Pathing`) and `Flatspace` (e.g. `Flatspace.Objects.Production`,
  `Flatspace.Objects.Resource`). Match whatever the file/folder you're editing already uses.
- **Misspelled identifiers are load-bearing.** Serialized/public names like `IntialBoardState`,
  `InitGameFromGaveSave`, and various `Grotsit`/`Grotsits` mixes are referenced from Unity scene/prefab
  YAML and from JSON save keys. Renaming them silently breaks serialization — only rename with a
  matching Unity script-rename + asset migration. (Purely private, code-only misspellings are safe to
  fix normally; `PlayerAI.CompleteResearch` and `Planet.GetMaintenanceCost` were two such fixes.)
- `Planet.UpdatePlanet` mutates shared `Planet` state and appends to the passed result list; it is not
  pure. The AI reads planet state back out during `ProcessResults` in the same turn.
- "Grotsits" is the game's consumer-goods resource; low grotsits lowers `Morale`, which scales all
  production.
- The Production and Research catalogs spell the WarShip subtype **`"Warship"`** (lowercase *s*), not
  `"WarShip"` — every `subType` string comparison in code must match that exact casing.
- **`UIDocument.rootVisualElement` is not the visible panel.** It's Unity's auto-generated root
  container for the whole document and stretches to fill the entire screen regardless of how the
  panel is positioned/sized in the `.uxml`. Bounds-testing against it (e.g. "is this click inside
  the panel?") always matches — query the actual named child element (e.g.
  `rootVisualElement.Q<VisualElement>("PlanetDetailElement")`) and test its `worldBound` instead.
- Generated / large directories are git-ignored: `Library/`, `Temp/`, `obj/`, `Logs/`, `UserSettings/`,
  `Recordings/`, and all `*.csproj` / `*.sln` files.
